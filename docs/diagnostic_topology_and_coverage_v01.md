# 較大拓譜與演算法情境清單

2026-10-14。目的：找出錯誤及尚未定義的情況，不以全部測試通過當作正確性證明。

## 先看什麼

1. 看 `output/diagnostic_topology_20261014/topology_and_contacts.png`。
2. 對照 `configs/diagnostic_topology_20261014/contacts.csv` 與 `bundles.csv`。
3. 優先看案例12：早到可以接收，卻不能等待；晚到才能完成整條路徑。

這是人工設計的診斷拓譜，不是NASA或學長的實際拓譜。12節點／32條有向contacts／5包，包含分流、匯流、不同時段的同一對節點、回程與跨層連線。節點多不代表涵蓋的錯誤多，因此另設12個可手算的小案例。

## 模型與輸入

| 項目 | 設定 |
| --- | --- |
| 節點 | S1、S2、S3、A、B、C、D、E、F、G、H、T |
| Buffer | S1/S2/S3/T為4MB，其餘為2MB |
| 單位 | 秒、MB、MB/s；MB採十進位 |
| 時間範圍 | 0～24秒；目前驗證格點間隔1秒 |
| 傳輸速率 | 一般1MB/s；c31為0.25MB/s |
| 傳播延遲 | 一般0；c32為2秒，為人工診斷參數 |
| Bundle | 固定依b1～b5順序規劃；前4包1MB，第5包2MB |
| 初始占用 | 大拓譜為0，後續由接受的路徑更新 |

目前測的是PPT後續獲授權的四欄Label、允許循環、保留全部Label的枚舉驗證程式，參考 `ppt_label_setting_cycles_pseudocode_v01.md`。舊 frozen v04 文件不是本次實驗定義。**動態可用contact區間尚未實作；本次不能當作該候選方法的驗證。**

小案例中的background是刻意指定的既有占用曲線，用來隔離判別式；不宣稱每條曲線都已由另一個完整bundle排程重建。大拓譜則從空占用開始，逐包完整提交。

## 動態contact的候選修改順序

1. 保留原始物理contact；另算本包的可起送區間，不覆寫原始時窗。
2. 先做單contact的接收端區間計算，與現有逐格檢查比較：格點上的可行時間應完全相同。
3. 將區間接到Label延伸，再檢查發送端等待／發送與同contact傳送衝突。
4. 用案例12確認較晚起送方案沒有消失；未證明前不能將每段縮成最早一點。
5. 有錯先保留輸入與差異；確認修正後才比較執行時間或接受率。

這是候選工作順序，不是已獲證明的新演算法。本次未更動路由、Label欄位或dominance。
