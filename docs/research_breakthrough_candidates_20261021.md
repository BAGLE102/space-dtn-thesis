# 目前困境的突破口評估

日期：2026-10-21。研究判斷與候選方向；未改演算法、未量測效能、未確認新穎性。

## 結論

優先探索：**依搜尋需求計算可行起送時段，並對資源變動做局部更新，降低逐包路徑規劃的成本。**

理由：可沿用既有 Contact Plan、buffer 曲線與具體 Label，不必靠新增模型限制製造差異；可先在相同模型下驗證效果。這是最值得先做診斷的方向，不是已成立的論文貢獻。

前一輪把逐 byte 當作首選，仍有兩個風險：差異可能只是整包預留與逐 byte 計量的不同，以及系統未必支援送出時立即回收儲存。因此把它保留為有條件的第二條路，先核對實作需求。

## 1. 困境的核心

- 原問題與 2410.15546v3 的 FEAP-CB 高度相關；contact splitting／forecast buffer／等待跨溢位剪枝已有先例。
- 目前候選加入了獨立 quota、容量歷史、循環、事件端點等複雜性，但尚未證明這些就是實際需求或優勢來源。
- 寫更多 Label 欄位、換搜尋名稱、跑更多 bundles，都不會自動形成貢獻。
- 真正要找的是：相同需求下，既有方法在哪類輸入付出可避免的計算，或哪個有實務依據的限制尚未處理。

## 2. 本次查核的文獻依據

### 2410.15546v3（讀取正文）

- §IV-B2 與 Algorithm 2：bundle-specific buffer 切割與搜尋內 edge pruning，不能說作者所有操作都在搜尋前完成。
- §VII-B、Fig.15：作者的小規模情境呈現很小的 Contact Plan 增量。因此「contact 一切就會爆炸」不是已證事實。
- §IX：大規模計算成本、較長規劃時域、突發流量、資訊誤差等尚未完整評估。這支持檢驗擴展性的研究動機，但不證明我們比較快。
- §VIII 已談 priority-specific plans 與低優先流量重排。不能只增加優先權／搶占便宣稱填補空白。

來源：https://arxiv.org/html/2410.15546v3

### TSRCG／RMDG-CGR（本次只核對摘要）

Sun 等人 2022 工作已研究 route-list、dynamic route computation 與計算／儲存資源改善。因此泛稱「減少 CGR 計算成本」不足以建立新穎性，下一步須對照其實際資料結構與快取／更新程序。

來源：https://arxiv.org/abs/2209.13227

本次定向搜尋不足以證明全領域沒有人做過 on-demand／incremental 區間搜尋。正式貢獻主張前仍須擴大相關工作與引用鏈查核。不能把搜尋沒命中當成不存在。

## 3. 第一選擇：搜尋時按需求解，預約後局部更新

問題敘述：

> 在保持既定 buffer／contact 模型的可行性與最早抵達結果下，能否避免每包重做無關區域的可行時段處理，降低規劃時間與記憶體？

具體候選：

1. 原始 contacts 保留穩定 ID；已接受傳輸時槽與節點占用曲線獨立記錄。片段可以作查詢結果，不必全部變成常駐 graph vertices。
2. Q 取出 Label 後，只對它實際探索的 outgoing contacts 查詢可行起送區間。
3. 查詢仍須包含完整傳輸時長、傳播延遲、傳送預約與送收 buffer；不能只找接收點「空閒開始」就當成可用。
4. 對每條 contact／bundle size／相關資源版本，可快取與前驅無關的區間結果。deadline、模型語意或查詢範圍若影響結果，也須納入 key 或另作裁切。
5. 前驅抵達時間與可等待範圍每次重新裁切；不能直接把某 Label 的最早起送答案沿用給其他 Label。
6. 接受一包後，只對其使用的 contacts、造訪節點的相關相交時間範圍使快取失效；先用較保守的節點版本失效確保正確，再評估細粒度失效。
7. 每個連通片要保留必要候選；這不授權「每條 contact 永遠只產生一個最早 Label」。原候選最早點與 dominance 的一般證明仍待完成。

這是候選實作設計，不是立即採用的新演算法。需先確認與既有按需查詢、隱式圖、增量路由方法的差別。

### 最小診斷，不必先寫完整搜尋

先建立相同資源查詢介面的兩種實作：全量建立本包可用片段、依相同查詢序列按需建立片段。先比較查詢答案一致性，再比生成量與成本。

隔離實驗可固定同一批「待探索 contact」查詢序列；這只能衡量資源處理元件，不能冒稱端到端路由加速。後續才接相同搜尋與 tie-break，報 preprocessing＋search＋commit 總時間。

診斷輸入須同時有：

- 大量節點但搜尋僅走少量區域：測是否避免無關處理。
- 高連通或無路徑需全面搜尋：測按需管理額外開銷。
- 高占用與大量碎片、窄時槽：測區間處理成本。
- 同大小重複 bundles 與大小多變 bundles：測快取受益與失效。
- 局部資源變動與大量變動：測增量更新是否值得。

通過門檻：相同模型與查詢答案一致；代表性情境有可重現成本改善；全掃描／頻繁失效時的退化也公開。若只在不合理的強造拓譜受益，不能作主要結論。

## 4. 第二選擇：精確逐 byte 可行時段

具體機會：前包在 B 釋放資料的同時，新包接收，總量未超限；求出這種部分重疊的可行起送區間。

成立前提：有系統依據允許逐 byte 釋放及同時收送；獨立核對既有方法的正式模型與實作。若兩方採不同 buffer 模型，應主張模型／求解能力差異，不能直接說既有搜尋錯誤。

推薦順序：先驗證實務與一個解析案例，再決定是否深入完整區間求解及新穎性查核。沒有物理／軟體依據則不要把它當研究主線。

## 5. 第三選擇：有限範圍調整前包，改善整批接受率

具體機會：先來 bundle 的最早路徑占掉某 bottleneck，但它其實有另一條仍符合 deadline 的路；調整少量舊預約後，可以接納原本失敗的新包。

測試用例可從兩包與兩條路開始，證明固定逐包順序可能犧牲總接受量；這是不同於單包最早抵達的目標。

風險：聯合排程、admission control、priority／preemption 已有大量相關工作，且此文 §VIII 已談重排。要聚焦具體的有限重排規則、代價、可行性與公平性，而非泛稱整體最佳。改動研究範圍大，目前列備選。

## 6. 判斷與下一個工作單位

| 候選 | 可沿用目前工作 | 最關鍵風險 | 優先 |
|---|---|---|---|
| 按需區間查詢＋局部更新 | 高 | 可能已有先例、實際不比好的切割實作快 | 第一 |
| 逐 byte 精確起送區間 | 高 | 系統不支援或僅是模型差異 | 第二，有條件 |
| 有限前包重排 | 中 | 目標改變、已有相關方法、實作更大 | 備選 |

下一步建議：核對 CGR 增量／快取與隱式時間圖文獻；建立小型「全量 vs 按需」查詢診斷，不改 Q／Label／dominance；以查詢一致性與實際總成本決定是否值得接入路由搜尋。

若不成立，保留負面結果並換方向。以上不表示候選完整正確，也不表示三個方向都要實作。
