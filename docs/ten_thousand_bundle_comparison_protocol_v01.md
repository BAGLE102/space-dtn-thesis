# 一萬包實驗與第一個對照組

## 現況

一萬包可以作為實驗目標，但目前沒有完成一萬包測試，也沒有可靠耗時估計。先前20秒上限包含搜尋、獨立完整列舉、資源檢查與輸出，不能直接外推搜尋一萬包的時間。

一萬包是總需求數，不等於一萬包同時傳送。分散一天生成與同時生成是不同負載；使用者尚待選擇。不能沿用10秒、同一條兩跳走廊，把大多數因期限未送達的包當作有代表性的整天結果。

## 已實作的第一個對照組

`src/ppt_validation/baseline_single_label.py`：每個節點僅保留完整抵達最早的一個有效Label，較晚或相同抵達者捨棄。回溯所需歷史Label仍保留。

- 共用相同contact、時間格點、容量、逐byte Buffer、發送預約及完整接收後轉送限制。
- 沿pred核對同contact累計使用量，成功路徑採相同完整排程驗證與逐包資源提交。
- 同時間以建立順序決定保留者，不額外替某一方法挑有利順序。
- 這是簡化的貪婪對照，不是完整CGR或SABR，不能把它未找到路徑稱為數學上無解。
- 它可能漏掉較晚抵達卻能接續的候選，也可能漏掉需要繞圈的解；這是本對照要檢查的候選保留差異。
- 不能拿此對照組結果宣稱優於完整標準路由。正式SABR定義見CCSDS 734.3-B-1：https://ccsds.org/Pubs/734x3b1.pdf 。

每個方法均從相同初始資源獨立執行，再更新自己的預約，沒有讓對照組使用另一方法已扣過的資源。每條成功路徑都通過完整獨立排程核對，資源提交也與獨立實作比對。資料在`output/single_label_baseline_20261013/comparison.json`。

22項相關測試通過，包括對照組漏解的已知PPT例子。對照組不承諾完整性，所以這個漏解不是目前待測方法的同模型反例。沒有改動你的搜尋演算法或自動加入新的支配規則，沒有進行執行速度比較。

## 一萬包的執行設計（尚未執行）

1. 先明確選擇生成方式：一天分散生成，或同時生成壓力測試。
2. 固定Ring Road輸入版本、KB單位、傳播延遲假設及節點Buffer，兩組使用完全相同的需求清單與處理順序。
3. 規劃100→1,000→10,000包的階段，較小階段確認能完成後再擴大；固定亂數種子，多個種子需預先列明，不依結果挑選。
4. 大規模每條接受路徑仍完整核對時間、容量、Buffer與發送預約；獨立完整列舉限小案例，不逐包對一天Contact Plan做完整列舉。
5. 大量輸出採每包摘要與選定路徑，詳細Label／Q紀錄限診斷個案；這需要另作執行層改動，不偷偷改路由判斷。
6. 只量測搜尋的時間，核對器／輸出另計。所有計時及資源預算對兩組採相同規則。
7. 超時、記憶體或Label上限標示INCOMPLETE，不算無路徑；整組未完成不宣告某方法勝出。

## 比較指標

- 每組完成查詢數、可行包數、未找到包數及未完成包數，分開呈現。
- 送達率只在完整完成且相同需求清單下比較。
- 兩組都送達的相同bundle比較抵達時間；另列僅某組送達者，避免把失敗需求排除後得到偏頗平均。
- 搜尋時間平均／最大／最小／標準差，並另列驗證及輸出成本。
- 每包建立／展開的Label數、記憶體用量、各節點Buffer峰值及contact利用率。
- 一萬包時沒有逐包完整列舉的真正最優值，不宣稱已知最優誤差；小案例另報對完整列舉的誤差。

## 尚待使用者選擇

生成時間採一天分散或同時生成。完整CGR／SABR對照尚未實作，本輪只完成上述單Label對照的定義及小案例核對。
