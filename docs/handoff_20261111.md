## 1. 問題設定

- 排程式（scheduled）DTN：所有 contact 的開關時間、速率 r、傳播延遲 d 事先已知（contact plan）。
- 多個 bundle 依固定順序逐包規劃。前面接受的包不再改動，會占用連線時段與節點 Buffer。
- 每一包的目標：在連線不重疊、Buffer 不超過上限 M 的條件下，找最早到達目的地的排程。找不到就拒絕（未送達）。
- Store-and-forward：中繼必須整包收完才轉送（`relay_ok` 要求 s₂ ≥ A）。同一節點可同時收、送（不同連線）。

## 2. 演算法（`dtn/ours.py`）

Label `L = (c, [lo, hi], pred)`：走 contact c，出發時間區間 [lo, hi]。

優先佇列 Q 的 key = lo + S/r + d（到達時間）。`reached` 記錄每條 contact 已到達過的時間，用來去重。

```
search：
  對來源每條往外 contact c：
    parts = candidate_range(c, g) → source_filter
    若 c 通到目的地 → destination_filter；insert
  while Q：取出最小 key 的 L1；若 L1 到達目的地就結束
    head = L1.lo + L1.c.d + S/L1.c.r
    對 L1 到達節點的每條往外 c2：
      parts = candidate_range(c2, head) → buffer_filter(parts, L1, c2)
      若 c2 通到目的地 → destination_filter；insert(c2, parts, L1)
backtrack：最後一跳取 lo；往前每跳取 min(hi, s_next − d − S/r)（盡量晚送）
validate：獨立重檢（不呼叫搜尋或篩選函式）
commit：寫入連線預約 F 與節點占用 O_n
```

### `candidate_range`（連線限制）

- 出發時間範圍：lo = max(a, head)，hi = min(b − S/r, T − S/r − d)。
- 對連線預約 F 中每筆 (x, y)，扣掉開區間 (x − S/r, y)。

意義：同一條連線同一時間只傳一包，用全部速率。只扣掉別包正在傳的那幾秒，其餘時間可用。

範例（程式輸出）：連線 100～120，已有預約 (105, 115)，新包傳 1 秒 → 可用出發時間為 [100, 104] 與 [115, 119]。

### Buffer 篩選

在每次建 Label 之前做，順序是 Range → Buffer 篩選 → Insert。搜尋時只知道出發時間區間，不知道確切時間；確切時間由 backtrack 決定。

每個篩選分兩段：

1. **快速判斷**：`O.peak(視窗) + S ≤ M` 時，整段保留，跳過細算。這是最壞情況，因為 own(t) ≤ S。
2. **細算** `solve_region`：用 O 的轉角及其平移位置把 [lo, hi] 切段。
   - 每個切點用 `*_ok` 單獨測。
   - 每段內，每個檢查點的值都是出發時間 s 的一次式。在 1/3、2/3 處取值得到斜率 k，解出上界或下界，取交集。
   - 各段結果用 `merge` 合併。

中繼 `buffer_filter` 的作法：對每個候選 s₂，前一跳只測 s₁\* = min(L1.hi, s₂ − d₁ − S/r₁)，與 backtrack 的規則一致。

注意：中繼篩選的變數是下一跳出發時間 s₂，不是「前一跳最早何時能傳」。

## 3. O_n（節點 Buffer 占用曲線，`dtn/model.py` 的 `Curve`）

### 資料結構

每個節點一個 `Curve`，包含三個清單：

- `ts`：轉角時刻，由小到大。
- `ls`：左極限，剛到這一刻之前的值。
- `rs`：右極限，剛過這一刻之後的值。

所有數值用 `Fraction` 精確計算。讀法：

- 兩點之間：從前一點的 rs 連直線到後一點的 ls（`_between`）。
- 同一點 ls ≠ rs：瞬間跳。
- 最後一點之後：延續 `rs[-1]`。

### 查詢

- `left(t)`、`right(t)`：t 的左、右極限，用 bisect 找位置。
- `top(t)` = max(left, right)。
- `between(a, b)` = `ts[bisect_right(ts, a) : bisect_left(ts, b)]`。
- `peak(a, b)` = max{top(a), top(b), between 內每個轉角的 top}。分段直線的最大值只會出現在端點或轉角。

### 寫入（`validate.py` 的 `commit`）

符號：h = s₁ + d₁（開始收），A = h + S/r₁（收完），f = s₂ + S/r₂（送完），f₀ = s₀ + S/r₀（來源送完）。

| 節點 | ts | ls | rs |
|---|---|---|---|
| 來源（g < s₀） | g, s₀, f₀ | 0, S, 0 | S, S, 0 |
| 來源（g = s₀） | s₀, f₀ | 0, 0 | S, 0 |
| 中繼（A < s₂） | h, A, s₂, f | 0, S, S, 0 | 0, S, S, 0 |
| 中繼（A = s₂） | h, A, f | 0, S, 0 | 0, S, 0 |
| 目的地 | h, A | 0, S | 0, 0 |

疊加方式 `O[n] = O[n].add(cv)`：轉角取聯集，左右極限分別相加，再用 `_prune` 刪除共線且無跳變的點。

同時把每一跳的 (s, s + S/r) 加入該連線的 F。

### 檢查（`stay_ok`）

條件：停留期間每個 t 都滿足 O(t) + own(t) ≤ M。只檢查以下各點：

- 起點：用 `right`。
- 終點：用 `left`。
- own 的轉角與 O 在區間內的轉角：用 `top`。

各角色的 own(t)，其中 ramp(t, a, b) 表示從 a 到 b 由 0 線性升到 S：

- 來源 `source_ok`：S − ramp(t, s₀, f₀)，停留期間 [g, f₀]。
- 中繼 `relay_ok`：ramp(t, h, A) − ramp(t, s₂, f)，停留期間 [h, f]，且 s₂ ≥ A。
- 目的地 `destination_ok`：ramp(t, h, A)，停留期間 [h, A]，在 A 瞬間交付。

### 模型假設（論文需寫明）

- 傳輸視為連續：收多少占多少，送多少空多少，不是送完才釋放。
- 來源從產生時刻 g 起就占整包。
- 目的地收完瞬間交付歸 0。

這比「整包預留」（peak + S ≤ M）寬鬆，三者是包含關係：舊規則（有占用就整段停用）⊆ 整包預留 ⊆ 逐步使用，三者都保證不超過 M。

可補的對照：改成送完才釋放。這會改動演算法，需使用者確認。

## 4. 對照組 SR-CGR（`dtn/srcgr.py`，簡化版）

- 用 Yen 演算法找 k 條簡單路徑，Dijkstra 的 cost 是到達時間。每跳用 `fit` 盡早送，會避開 F，但選路時不看 Buffer。
- 依序拿去 `validate` 回放，取第一條通過的；全部失敗就拒絕。k=1 記為 sr1，k=10 記為 sr10。
- 和文獻版 SR-CGR 的差別：文獻版會重試、在中繼重新選路，送達率常為 1，比較的是延遲和改路次數。簡化版容易被質疑是「稻草人」對照組。

## 5. 實驗與結果

### 5.1 隨機拓樸（`src/experiments/dtn_validation/`，`config.json`）

- 拓樸：20 節點／600 contacts，以及 40 節點／1,600 contacts。horizon 3,600 秒，contact 長度 30～300 秒，速率 1／2／5，延遲 0～0.5。
- 流量：bundle 1 MB，產生時間在 0～600 秒（release 600），包數 N = 100／300，OD 對隨機抽取（可重複）。
- Buffer M = 3／30 MB，10 個種子。
- 已有結果（數字見 CHANGELOG 與 1103 簡報 v1.26）：
  - 3 MB 時送達率明顯低於 100%。診斷：產生時間集中、contact 稀疏、Buffer 只能放 3 包、來源從 g 起占用；不是程式錯誤。
  - 同狀態比較（`diagnostics/same_state/`，照本方法的提交順序重放，共 4,000 包）：
    - 兩邊都可行時，本方法從未比 SR-CGR 晚。
    - sr1 可行時，結果與本方法相同。
    - sr10 有 6～78 包較晚。
    - 只有本方法可行的有 16～283 包；只有 SR 可行的為 0。
    - 不限 Buffer 時，100% 有路。
  - 正確性測試（非證明）：
    - 與窮舉（`oracle.py`，1/16 秒格點）比對，4,701 個小案例、9,311 次查詢，本方法較晚或產生不合法排程的次數為 0。
    - 拿掉來源／中繼／目的地篩選時，會出現 79／27／32 個不合法排程，表示測試抓得到錯。

### 5.2 Iridium（`src/experiments/walker/`）

- 拓樸：依 ns-2 內建 Iridium 模型的設計參數。
  - 6 個軌道面 × 11 顆，高度 780 km，傾角 86.4°。
  - ISL：同軌道面前後常連；相鄰軌道面在 |緯度| > 60° 時斷開；不跨 seam。
  - 地面站仰角 ≥ 8.2°。
  - 速率：ISL 25 Mb/s，上下行 1.5 Mb/s。
- 自行決定的部分：
  - 圓軌道、無攝動。
  - 相鄰軌道面錯開半個間距。
  - GS1 土魯斯 → GS2 台北。
  - 地面站 Buffer 不限（背景占用 −1e9）。
- 流量：每包 1 MB，在 2,000 秒內等間隔產生。

結果（`results/iridium_nb500_1000.*`）：

| 包數 | 衛星 Buffer M | 本方法 | sr1 | sr10 |
|---|---|---|---|---|
| 500 | 2 | 100% | 91.2% | 93.2% |
| 500 | 5 | 100% | 95.6% | 99.4% |
| 500 | 10 | 100% | 99.0% | 100% |

- 計算時間：本方法每包中位數約 0.35 秒，SR 約 0.06 秒。
- 1,000 包、M = 2：只跑完本方法，送達率 100%，平均延遲 715 秒，總計算 5,990 秒（每包中位數 5.6 秒）。其他組合以及 2,000 包因執行時間上限中止，沒有結果。
- 只比三種方法都送達的包時，本方法延遲較大（M=2 時 22.2 秒 vs sr1 14.1 秒）。原因是本方法多收的包占用了資源，各方法的狀態不同，所以這不能當作路徑好壞的比較，需要在 Iridium 上做同狀態比較。
