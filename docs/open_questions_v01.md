# 現行演算法待釐清問題（2026-10-12）

基準：[`sequential_label_setting_v04.md`](sequential_label_setting_v04.md)、[`current_algorithm_snapshot_v01.md`](current_algorithm_snapshot_v01.md)。本清單區分「現行模型內的正確性」、「模型與實際傳送的差距」、「效率與論文比較」。它記錄問題與所需證據，不採納新規則，也不改動 frozen v04。

## 先釐清的三件事

| 順序 | 問題 | 已知事實 | 需要釐清／完成標準 |
|---|---|---|---|
| 1 | 論文究竟主張解哪個問題？ | 現行搜尋解有限格點、aggregate quota、既有 Buffer 預約固定的單包最早完整抵達問題；已有兩包同時占用同一 Contact 的實體排程反例。 | 明確選定第一階段只主張 aggregate 模型，或另立 transmission calendar 模型；若主張實際可執行排程，必須檢查每次傳送的時段。不能把兩種可行性混稱。 |
| 2 | Label 與 dominance 的固定 SOP 是什麼？ | 現行程式對一個 `(Label, Contact, 開始時間)` 先做時間／容量／Buffer 延伸檢查；通過才建立候選 Label，接著和同節點有效 Labels 比支配，最後入 Q。L1（c3、到 B=2）與 L2（c4、到 B=8）均保留。 | 把比較時實際已知的資料、逐項檢查順序及「比較過但不支配」原因寫成一份 trace 表；證明刪除 Label 後不會失去可行或更早到達的後續路徑。 |
| 3 | 「接收點哪些時間能用」應如何定義？ | 已接受 bundles 的完整路徑與每跳時間可生成固定的 `O_v(t)`；目前程式已在每個候選開始時間檢查接收端逐 byte 占用。 | 決定要維持逐格檢查，或先計算可用開始時間集合。若預先篩選，必須證明它與原逐格檢查在同一模型下等價，不能只用「整段完全空閒」當條件。 |

## 正確性問題：先於效能比較

| ID | 待釐清事項 | 為什麼重要 | 最小驗證方式 |
|---|---|---|---|
| C1 | **支配判別的安全性與保守程度**：同節點、較早抵達、能持包等待、各 Contact 已用量不更多，是否構成足夠的後續可替代條件？有沒有可安全放寬的部分？ | 現行規則是充分條件候選，可能留下大量 Labels。拿掉用量比較不能直接做：若後續重用同一 Contact，前綴用量會影響 quota。 | 先給後續替代的逐步論證；對欲放寬的每條條件建立最小反例與獨立完整搜尋比對，再決定是否提出修改。 |
| C2 | **Buffer 判別的時間範圍**：接收時可行，收完後能否等到下一跳？ | L1 在 B 第 2 秒完整抵達時可建立，但不能持包跨過第一包的 B 占用高峰。 | 分別列出接收曲線 `[h,a']`、下一跳等待／發送曲線 `[a',s]`、`[s,f]`；對照 trace 與手算峰值。建立 Label 時不預判尚未選定的下一跳。 |
| C3 | **可用開始時間集合**：若預先產生，輸入是 Contact、bundle 大小、目前 Label 的抵達時間、固定 `R/O`；輸出究竟包含哪些 s？ | 接收端只是一個限制；傳送端 Buffer、時窗、aggregate quota、傳播延遲與時間上限也會淘汰 s。等待可行性又取決於 Label 的抵達時間，不是節點的一張永久靜態「空閒表」。 | 先以現有逐格枚舉作參考，逐一比較每個 s 的 PASS／FAIL 與理由；包含「前段失敗、後段可行」、部分占用但可逐 byte 接收、同時事件及非零延遲。 |
| C4 | **格點內完整性與終止**：時間枚舉、支配後第一次取出有效目的地 Label，是否總保留最早完整抵達路徑？ | 已有條件式論證與有限小例比對，但不等於一般性實作證明；`NO_ROUTE_ON_GRID` 也不代表連續時間無解。 | 整理前綴可行、後續替代、有限終止與最早抵達的完整證明；擴充獨立完整搜尋的邊界案例。若發現同模型反例，保存並停止後續效能比較。 |
| C5 | **狀態與回溯**：論文顯示的 `(c,A,s,pred)` 能否還原 Contact 使用量與完整等待區間？ | 四欄位是儲存／呈現方式；對 quota 與支配有影響的前綴用量仍是數學狀態，不能因畫面不顯示就當它不存在。 | 用包含重訪節點與重複使用 Contact 的案例，檢查由 pred 鏈重建的用量、時間與獨立檢查一致。 |

## 模型與實際傳送的距離

| ID | 待釐清事項 | 已知證據／決策點 |
|---|---|---|
| M1 | **Contact 的實際忙碌時段** | [已保存的同時傳送反例](../output/research_audit_v01/counterexample_sequential_overlap.json)證明 aggregate quota 通過不保證同一 Contact 可實際發送。若加入 transmission calendar，需重新定義可行性、延伸與預約，不只是顯示剩餘總量。 |
| M2 | **Buffer 的計量層級與釋放時點** | 目前採逐 byte 接收／發出即釋放、完整接收後轉送、同時事件以峰值上界判定。須說明這代表哪一層儲存、是否保留重傳副本，以及同時生成／交付／發送的先後。 |
| M3 | **中央規劃器實際知道什麼** | 第 k 包搜尋時只應使用前 k−1 包已接受的完整預約；候選 Labels 不互相預約。要界定是事前批次規劃或線上規劃，以及控制資訊何時到達節點。 |
| M4 | **逐包順序與拒收語意** | 固定順序的每包最早抵達不保證整批最好；同值路徑可改變後包資源。須固定排序／同值規則，定義拒收、重試及未傳 bundle 是否仍占來源 Buffer。 |
| M5 | **時間格點與有效期** | 已有連續時間更早解的反例；須明確區分 `T` 是計算截止或 bundle deadline。若研究連續時間，需另證可行出發時間集合的完整性。 |

## 效率、比較與貢獻：待前述問題收斂後處理

| ID | 待釐清事項 | 需要的證據 |
|---|---|---|
| E1 | 時間枚舉與 Label 數量是否能承受較大拓樸？ | 固定模型與資料後統計候選數、保留／淘汰 Labels、執行時間與記憶體；區分核心搜尋與 trace／網站記錄成本。 |
| E2 | 預先計算可用開始時間是否有價值？ | 先證同模型等價，再比較逐格檢查與預先產生集合的成本；不能只展示某個案例少檢查幾次。 |
| E3 | 與既有方法能否公平比較？ | 固定相同 bundle、Contact、quota、Buffer、時間模型與處理順序；列出哪些 baseline 原本解不同問題，哪些是改編版本。 |
| E4 | 論文貢獻究竟是什麼？ | 不把 Label Setting、傳輸時間或 Buffer 檢查單獨宣稱首創；依確定的模型差異、證明與同模型比較結果寫出可支持的主張。 |

## 建議的下一個工作單位

先只處理 **C1–C3**：用 PPT 第二包逐筆列出 L1、L2、L3 建立與比較時已知的 `R/O`、各 Contact 前綴用量、Buffer 檢查時間範圍及 Q 更新。接著把「預先判斷可用開始時間」寫成候選規格，與目前逐格判別對照。這是定義與驗證工作；若結果指出現行規則有同模型錯誤，保存案例並提出候選修正，不自行改 frozen v04。
