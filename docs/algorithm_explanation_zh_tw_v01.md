# 目前演算法的中文說明

本文件只調整說法，演算法仍是 v04。用詞對照見 [本研究的用詞說明](terminology_zh_tw_v01.md)。

## 我們要解的問題

依指定順序處理多個 bundles。前一個 bundle 的路徑與發送時間確定後，記錄它使用的資料量與 buffer 占用時段。處理下一個 bundle 時，必須考慮這些已排定的占用。

每次找路的目標，是讓目前這個 bundle 在符合限制的情況下，最早完整到達目的地。這不保證所有 bundles 一起考慮時也得到最佳排程。

## 一次搜尋使用哪些資料

- 每個 contact 的起訖時間、傳輸速率、傳播延遲及剩餘可分配資料量。
- 各節點的 buffer 上限，以及先前已排定的占用時段與占用量。
- 目前 bundle 的來源、目的地、生成時間與大小。

這些資料在一次搜尋中保持不變。不同候選路徑不會互相占用資源，只有最後選定的路徑才更新預約。

## Label Setting 如何找路

1. 在來源建立一個標籤（label），記錄目前節點、整包到達時間與已使用的資料量。
2. 從優先佇列取出到達時間最早的標籤。
3. 逐一嘗試下一個 contact，並嘗試允許的發送時間。
4. 檢查能否在 contact 結束前傳完整包、可分配資料量是否足夠，以及兩端的 buffer 是否超量。
5. 通過檢查就建立下一個標籤，再用支配規則（dominance rule）判斷哪些標籤不必繼續搜尋。
6. 取出目的地的有效標籤後，還原路徑與發送時間，確認後更新資源預約。

## 如何判斷標籤能不能刪除

對到達同一節點的兩個標籤，較早到的標籤必須能等到較晚者的到達時間，而且各 contact 已用的資料量不更多，才能取代較晚者。

「能等待」的意思是整段等待期間都不會超過 buffer 上限，不是等待沒有時間影響或不占空間。

判斷式仍是：a1≤a2、O_v(t)+S≤M_v 對所有 t∈[a1,a2] 成立，以及 U1[c]≤U2[c] 對所有 contacts 成立。成立時，保留較早者不會失去較晚者所能提供的最佳結果。

## 我們做了哪些驗證

先逐步追蹤兩個 bundles 的搜尋過程，再用另一支獨立列舉驗證程式，列出小型案例的候選路徑與發送時間，分別計算可行性及最早到達時間，與目前演算法比較。

這支驗證程式不呼叫目前演算法的標籤延伸或支配規則。因此它的用途是提供獨立的參考答案；原文件稱為 oracle，後續說明不再單獨使用這個詞。

本輪 14 個案例、15 次搜尋結果一致，18 項測試通過。這是指定案例的驗證結果，不是所有問題都已證明正確。

## 目前仍有限制

- 目前只嘗試固定時間間隔上的發送時間，例如每隔 1 秒；尚未完成連續時間的搜尋方法。
- 目前只檢查 contact 的總可分配資料量，還沒有利用完整的已排定傳輸時段表來避免鏈路時間衝突。
- 等待會占用 buffer，也可能延後到達；本模型只是沒有另外設定等待費用或能量限制。
